# 触发器（trigger）用法

触发器 = **让未来的某一轮自动发生**。它由平台调度，不是你在当前会话里排个队。

## 0. 先确认你手上有什么

- 你必须有 `callServer` 工具，且被授权了 `trigger.*` 方法（`list` / `get` / `create` / `update` / `delete` / `run`）。
- 没有 `callServer` 工具 → 说明这个会话没开能力面，**直接告诉用户该怎么开，不要假装建成功了**。
- 不确定某个方法的参数 → 先 `callServer detail trigger.create`（参数以服务端 schema 为准，本文不抄）。

## 1. 什么时候该建触发器，什么时候不该

| 用户说的话 | 该做什么 |
|---|---|
| "每天早上 9 点检查磁盘" | 建 `cron` 触发器 |
| "20 分钟后提醒我关火" | 建 `once` 触发器 |
| "CI 挂了就来看看日志" | 建 `webhook` 触发器，让外部系统调 |
| "帮我看看现在磁盘" | **不建**，当场跑 |
| "跑完告诉我一声" | 不需要触发器，干完调 `postNotification`（它写的是**平台通知收件箱**，平台不做外部推送） |
| "每小时查一次，有变化才告诉我" | 建 `cron` + 指令里写清"没变化就不要通知"（见 §5） |

触发器是**长期存在的平台对象**，不是一次性的定时器。建之前先想清楚：它要不要长期跑？谁来收尾？失败了谁知道？

## 2. 选 source

| source | 适用 | 硬约束 |
|---|---|---|
| `cron` | 周期性、可按时钟表达 | 5 段表达式（分 时 日 月 周）；**最小间隔 5 分钟**（更密会被拒）；时区默认 `Asia/Shanghai`，跨时区任务必须显式给 `tz` |
| `once` | 一次性、延迟执行 | `at` 必须是将来；触发后自动停用（`maxRuns` 固定为 1，不要自己设更大值） |
| `webhook` | 由外部系统（CI、监控、告警）驱动 | 平台是**哑端点**：不做过滤、不做模板、不做去抖。事件解释留在外部系统 |

判断顺序：**外部系统已经有事件 → webhook；只发生一次 → once；其余周期性 → cron**。

不要为了"更实时"把 cron 设成 `* * * * *`——它会被拒（5 分钟下限），而且高频轮询会持续消耗会话与配额。

## 3. 选会话模式

| 模式 | 语义 | 什么时候用 |
|---|---|---|
| `new` | 每次触发开一个**新会话** | 按次回看、结果互不影响（巡检、单次任务） |
| `reuse` | 所有触发**共用一个会话**，上下文延续 | 需要连续性（长期跟踪同一件事、状态累积） |

`reuse` 还可以**绑定一个已有会话**（`sessionId`）：

- 有值 → 每次都写这个会话（idle 被回收后自动恢复）
- 空 → 第一次触发时自动创建，之后固定复用它
- 绑定的会话**必须是你自己 agent 的**（别人的会话会被拒）；绑定后该会话被删除 → 该次运行直接 `failed` 并通知你

选 `reuse` 前提醒用户一句：那个会话里会不断追加内容；如果会话已经被用于别的事情，`new` 更干净。

## 4. 写指令（prompt）的四条要求

触发时那轮**没有人在旁边**。指令就是那一轮的"任务书"：

1. **自包含**：不要写"按刚才说的那样做"——未来那轮的上下文里没有"刚才"。
2. **可独立执行**：写清看什么、判据是什么、什么情况下要报告。模型拿不到当前会话的任何临时约定。
3. **给判据，不要给情绪**：写"超过 90% 就告警"，不要写"注意一下磁盘"。
4. **明确"没事时怎么办"**：默认不打扰（"一切正常就只更新状态，不通知"）；但**失败**不需要你在指令里安排——平台会自动记 `failed` 并向通知中心写一条 error 通知（进 `/notifications` 收件箱）。

## 5. 触发后怎么汇报

那一轮结束时，把"人需要知道的事"通过 **`postNotification`** 送出去（需要本会话启用这个 server 工具）：

- 报告写结论与下一步（"磁盘 94%，已清理 /tmp 释放 12G"，而不是"我检查了磁盘"）
- `severity` 按影响选：`info` 例行、`warning` 需要关注、`error` 需要处理
- **不要**把原始日志、大段输出、secret 塞进通知
- 顺利但无事可报时就别发——通知是打扰，不是日志

## 6. 运行状态（读 run 历史时怎么理解）

`trigger.get` 会带最近若干次 run。四种状态：

| 状态 | 含义 | 你该做什么 |
|---|---|---|
| `fired` | 真的跑了一轮（`triggeredBy` 说明谁触发的：`schedule`/`webhook`/`manual`/`capability`/`plugin`） | 正常 |
| `skipped` + `overlap` | 上一轮还没跑完，本次跳过（不排队） | 说明任务比周期长，考虑拉长间隔或拆任务 |
| `skipped` + `duplicate` | 同一个 `Idempotency-Key` 在 24h 内重复到达（webhook 场景） | 正常，外部系统重试而已 |
| `skipped` + `disabled` | 触发器当时是停用状态 | 检查 `enabled` |
| `missed` | 平台停机期间错过的时刻，**只记一次、不补跑** | 需要补就跑一次 `trigger.run` |
| `failed` | 执行失败（含绑定的会话被删、agent 工作区不存在等），平台已写一条 error 通知进收件箱 | 看 `error` 字段再修 |

## 7. 几个容易踩的点

- **每 agent 最多 10 个启用触发器**；建满会被拒，先停用或删掉不用的。
- **停用后再启用会重算下次时间**（不会补跑停用期间错过的时刻）。
- **达到 `maxRuns` 会自动停用**；要续跑得先把上限提高。
- **webhook 的 secret 只在创建/轮换那一刻明文可见**：建完立刻把 secret 交给需要它的外部系统，不要写进回复、日志、会话文件。
- **`trigger.run` 不影响下次时间**，只是立刻跑一次——用它试跑很安全。
- 触发器只在**平台进程活着**的时候有效；停机期间的时刻会变成 `missed`。

## 8. 建完必须试跑

```
callServer detail  trigger.create      # 1. 看参数
callServer trigger.create  …           # 2. 建（webhook 会把 secret 明文返回一次）
callServer trigger.get     {id}        # 3. 看 nextAt 是否符合预期
callServer trigger.run     {id}        # 4. 立刻跑一次，验证指令真的能独立执行
callServer trigger.get     {id}        # 5. 看 run 历史：fired 还是 failed
```

第 4 步别省。无人值守任务最常见的失败不是调度错，而是**指令写成了"只有当时在场的人才看得懂"**。试跑发现的问题，用 `trigger.update` 改；建错了用 `trigger.delete`（历史 run 会保留）。

## 9. 别做的事

- ❌ 用触发器当"给用户发消息的通道"——它执行的是任务，要说话用 `postNotification`
- ❌ 把 webhook 的 secret 写进 prompt 或回复（prompt 会落在会话文件里）
- ❌ 建一堆只跑一次的 `cron` 来做延迟任务（那是 `once`）
- ❌ 期望错过的时刻被补跑、期望重叠的触发排队
- ❌ 建完不试跑就告诉用户"已经帮你安排好了"
